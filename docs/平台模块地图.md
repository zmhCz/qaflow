# 平台模块地图

## 1. 目标

这份文档用于回答三个问题：

1. 当前平台有哪些模块
2. 它们分别处于哪一层
3. 后续重构时哪些模块保留、哪些模块收敛、哪些模块下沉为公共底座

---

## 2. 当前模块总览

## 2.1 后端业务模块

| 模块 | 主要职责 | 当前定位 |
| --- | --- | --- |
| `users` | 用户、认证、登录、短信登录、Token 交换 | 平台基础能力 |
| `projects` | 通用项目、项目成员、项目环境 | 平台基础能力 |
| `versions` | 版本管理 | 平台基础能力 |
| `testcases` | 通用测试用例、步骤、附件、评论、导入 | 测试资产能力 |
| `testsuites` | 通用测试套件 | 测试资产能力 |
| `executions` | 通用测试计划、测试执行、执行用例、执行历史 | 执行管理能力 |
| `reports` | 通用测试报告模板与报告记录 | 报告能力 |
| `reviews` | 用例评审、评论、模板 | 测试治理能力 |
| `requirement_analysis` | 需求文档上传、分析、业务需求、生成用例、生成任务 | AI 测试设计能力 |
| `assistant` | Dify 配置、会话、消息 | AI 助手能力 |
| `api_testing` | API 项目、请求、集合、环境、历史、执行、定时任务、通知 | API 自动化子平台 |
| `ui_automation` | UI 项目、元素、脚本、页面对象、执行、AI 智能模式 | Web UI 自动化子平台 |
| `app_automation` | APP 项目、设备、元素、组件、场景编排、执行、调度、通知 | APP 自动化子平台 |
| `data_factory` | 测试数据与工具数据记录 | 公共数据能力 |
| `core` | 统一通知配置 | 平台公共能力 |
| `analytics` | 埋点与统计 | 可选平台能力 |

## 2.2 前端模块分区

前端当前以工作区形式组织：

- `/ai-generation`
- `/api-testing`
- `/ui-automation`
- `/app-automation`
- `/ai-intelligent-mode`
- `/configuration`

说明：

- 当前前端不是“统一平台首页 + 能力中心”
- 而是“多个子系统共享一个壳”

## 3. 按架构层划分模块

## 3.1 平台基础层

这些模块原则上应该保留，并逐步强化为平台公共底座：

- `users`
- `projects`
- `versions`
- `core`
- `analytics`

职责：

- 身份认证
- 项目与空间
- 成员与权限
- 公共配置
- 埋点与审计

## 3.2 测试资产层

这些模块代表平台应该统一沉淀的测试资产：

- `testcases`
- `testsuites`
- `reviews`
- `requirement_analysis`

职责：

- 测试点
- 测试用例
- 用例步骤
- 套件
- 评审
- AI 生成

现状问题：

- `requirement_analysis` 输出的对象，还没有完全纳入统一测试资产中心
- `ui_automation` 和 `app_automation` 里又各自维护了一套用例 / 套件

## 3.3 执行中心层

这些模块共同构成当前的执行相关能力：

- `executions`
- `reports`
- `api_testing` 的执行部分
- `ui_automation` 的执行部分
- `app_automation` 的执行部分

职责：

- 执行计划
- 执行任务
- 执行用例
- 结果收集
- 报告输出
- 通知

现状问题：

- 通用执行中心和各子平台执行中心并存
- 计划、任务、执行、报告没有一套统一抽象

## 3.4 自动化能力层

这些模块更适合被定义为“能力中心”或“执行适配层”，而不是平台顶层对象：

- `api_testing`
- `ui_automation`
- `app_automation`

职责：

- API 执行
- Web UI 执行
- APP 执行

建议定位：

- 保留业务能力
- 下沉为 Runner / Engine / Adapter 层
- 不再各自发展完整的平台对象模型

## 3.5 AI 能力层

当前 AI 相关能力分散在多个模块：

- `requirement_analysis`
- `assistant`
- `ui_automation` 中的 AI 智能模式
- `api_testing` 中的 AI 配置

建议重构为统一的 `ai-center`：

- 模型配置
- Prompt 配置
- AI 工作流
- 自然语言转测试资产
- AI 执行辅助
- AI 报告总结

## 4. 当前模块之间的关系

## 4.1 当前主链路

### 通用测试管理链

`projects -> versions -> testcases -> testsuites -> executions -> reports`

### AI 需求到用例链

`requirement_analysis -> generated test cases -> testcases / reviews / executions`

### Web UI 自动化链

`ui_automation project -> elements / page objects / scripts / cases / suites -> execution -> report`

### APP 自动化链

`app_automation project -> devices / packages / elements / components / scene-builder / cases / suites -> execution -> report`

### API 自动化链

`api_testing project -> collections / requests / suites -> execution -> report`

## 4.2 当前结构性问题

这几条链都各自成体系，导致：

- 项目模型不统一
- 用例模型不统一
- 套件模型不统一
- 执行模型不统一
- 报告与证据模型不统一

---

## 5. 推荐的目标模块地图

## 5.1 目标平台结构

推荐把当前平台重构为 8 个一级中心：

1. `identity-center`
2. `workspace-center`
3. `test-asset-center`
4. `execution-center`
5. `evidence-center`
6. `notification-center`
7. `ai-center`
8. `data-center`

## 5.2 自动化能力改为能力子域

原有：

- `api_testing`
- `ui_automation`
- `app_automation`

目标改造后：

- `automation-api`
- `automation-web`
- `automation-app`
- `automation-ai-browser`

它们作为执行适配层存在，不再承载平台级顶层对象。

## 5.3 推荐映射关系

### 平台级保留

- `users` -> `identity-center`
- `projects` + `versions` -> `workspace-center`
- `testcases` + `testsuites` + `reviews` -> `test-asset-center`
- `executions` + `reports` -> `execution-center` / `evidence-center`
- `core` -> `notification-center`
- `data_factory` -> `data-center`
- `assistant` + `requirement_analysis` + AI 配置 -> `ai-center`

### 执行适配层

- `api_testing` -> API Runner Domain
- `ui_automation` -> Web UI Runner Domain
- `app_automation` -> APP Runner Domain

## 6. 模块改造优先级

## P0：必须先动

- `projects`
- `testcases`
- `testsuites`
- `executions`
- `ui_automation`
- `app_automation`

原因：

- 这些模块决定平台对象模型是否统一
- 是后续 AI 接入和平台升级的地基

## P1：第二批改造

- `requirement_analysis`
- `reviews`
- `reports`
- `core`
- `assistant`

原因：

- 这些模块适合重构成平台能力中心

## P2：后续治理

- `analytics`
- `data_factory`
- `versions`

原因：

- 价值明确，但对平台结构影响没那么直接

## 7. 前端重组建议

## 7.1 当前问题

当前前端菜单是按子系统切换：

- AI 生成一套菜单
- API 一套菜单
- UI 一套菜单
- APP 一套菜单

问题：

- 用户心智被切碎
- 平台没有统一任务中心
- 平台没有统一资产中心

## 7.2 目标导航

建议改成：

- 工作台
- 测试资产
- 自动化中心
- 执行中心
- 报告中心
- 设备与环境
- AI 中心
- 系统配置

### 自动化中心下再分

- API 自动化
- Web UI 自动化
- APP 自动化
- AI 智能执行

---

## 8. 模块地图结论

当前系统已经具备平台雏形，但仍停留在：

**“多个测试系统共仓共壳”**

目标应该是演进到：

**“一个统一测试平台，下面挂多个自动化能力中心”**

这意味着后续重构的重点不是增加模块，而是：

- 统一对象
- 统一入口
- 统一执行
- 统一证据
- 统一 AI

---

## 9. 下一步建议

基于这份模块地图，下一步应进入：

- `统一对象模型草案`
- `执行中心重构设计`
- `前端信息架构重组`

其中最优先的是统一对象模型。
