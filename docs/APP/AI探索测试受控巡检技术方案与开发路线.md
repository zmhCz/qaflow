# QAFlow AI 探索测试受控巡检技术方案与开发路线

> 版本：v1.0
> 制定日期：2026-07-15
> 当前结论：以“目标清单驱动的受控巡检”作为默认主路径，自由探索作为高级辅助能力，AI 基于页面地图提供分析与受控决策。

## 1. 建设目标

QAFlow 当前自由探索执行器已经具备真机控制、截图、UI 树、日志、风险护栏、问题复核和 AI 报告分析能力，但控件选择仍以候选评分为主，容易偏离用户指定页面和目标。

本轮建设需要实现以下闭环：

1. 测试人员配置目标页面、目标控件清单和安全边界。
2. 平台严格按照目标清单执行，不命中时记录结果，不自由点击无关控件。
3. 每次操作形成前后截图、点击范围、页面结构、状态变化和日志证据。
4. 巡检结果持续沉淀为可复用页面地图，并与语义元素库关联。
5. AI 基于页面地图分析覆盖缺口、生成语义建议和下一轮巡检计划。
6. 后续逐步允许 AI 在平台校验、风险护栏和人工确认下参与执行决策。

## 2. 产品能力分层

### 2.1 目标巡检

默认推荐模式，适合页面入口遍历、控件可用性巡检和业务冒烟检查。

- 输入：起始导航、锚点页面、目标清单、最大滑动次数、最大深度、风险黑名单。
- 行为：只查找和操作目标清单中的控件。
- 找不到：标记 `not_found`，不点击其它候选控件。
- 进入子页面：采集证据后返回锚点；恢复失败时重启 APP 并重放起始导航。
- 输出：目标覆盖矩阵、页面地图、异常证据和语义元素候选。

### 2.2 自由探索

保留现有规则执行器，作为高级辅助模式，用于发现未知入口、崩溃、ANR、异常弹窗和低概率路径。

- 不作为目标覆盖率的主要依据。
- 报告必须明确标识为“非确定性探索”。
- 后续可以使用页面地图限制探索边界，减少重复访问和偏航。

### 2.3 AI 分析与决策

AI 第一阶段不直接控制手机，主要承担：

- 解释巡检结果和疑似异常。
- 推荐页面和控件的业务语义名称。
- 识别页面地图中的未覆盖区域。
- 生成下一轮目标清单和巡检草稿。
- 将稳定路径转换为自动化用例草稿。

后续 AI 参与执行时，只能输出平台定义的结构化动作，由平台完成参数校验、风险检查和最终执行。

## 3. 总体技术架构

```text
巡检任务定义
  -> 执行批次
    -> 目标调度器
      -> 页面状态采集
      -> 目标定位
      -> 风险校验
      -> 动作执行
      -> 状态变化判定
      -> 锚点恢复
    -> 页面地图服务
    -> 巡检报告
    -> AI 分析服务
      -> 下一轮巡检草稿
      -> 语义元素候选
      -> 自动化用例草稿
```

Android 首期继续使用 ADB、UIAutomator XML 和截图能力。执行器通过平台无关接口访问设备，为后续 iOS 的 WebDriverAgent/Appium 接入保留扩展空间。

## 4. 核心技术决策

### 4.1 新建独立目标巡检执行器

新增 `TargetInspectionRunner`，不继续在 `RuleExplorationRunner` 中堆叠目标巡检分支。

统一执行器接口建议包含：

```python
class ExplorationRunner:
    def prepare(self): ...
    def run(self): ...
    def stop(self): ...
    def build_summary(self): ...
```

任务分发根据策略选择执行器：

- `target_inspection` -> `TargetInspectionRunner`
- `rule_mvp/smoke/stability/form/list` -> `RuleExplorationRunner`

### 4.2 拆分任务定义和执行历史

现有任务重新执行时会删除历史步骤，无法支持趋势分析和报告对比。建议调整为：

- `AppExplorationTask`：任务定义和可复用配置。
- `AppExplorationRun`：一次执行批次，保存设备、版本、状态、结果和耗时。
- `AppExplorationStep`：关联执行批次，保留任务关联用于兼容旧数据。
- `AppInspectionTargetResult`：保存每个目标的执行状态和证据。

旧任务和旧报告必须继续可读，新执行从迁移完成后写入执行批次。

### 4.3 页面地图持久化

新增以下核心实体：

- `AppPageNode`：应用、平台、版本、Activity、页面指纹、业务名称、代表截图。
- `AppPageElement`：页面内控件快照、文字、resource-id、控件角色、归一化范围、风险等级、关联语义元素。
- `AppPageTransition`：来源页面、触发控件、动作、目标页面、成功次数、失败次数和可信度。

页面地图按项目、应用标识、平台和版本隔离。Android 包名和 iOS Bundle ID 不直接作为语义库的最高层业务概念，跨端页面通过业务页面标识关联。

### 4.4 页面状态判定

页面是否发生有效变化不能只判断 Activity 或完整 XML 哈希，需要组合判断：

- Activity/Window 是否变化。
- 稳定控件结构是否变化。
- 弹窗、底部弹层、Toast 是否出现。
- Switch 的 `checked/selected` 状态是否改变。
- 列表项数量或目标区域是否变化。
- 截图目标区域的感知哈希是否变化。

页面指纹生成时需要忽略时间、计数、随机昵称、动态列表内容等易变数据。

### 4.5 目标定位优先级

目标定位按以下顺序执行：

1. 已验证语义元素库。
2. 可见文字和 `content-desc` 精确匹配。
3. `resource-id` 和控件结构匹配。
4. 文字模糊匹配和可点击父容器提升。
5. 有限 OCR 或图像定位兜底。

每个目标允许配置最大滑动次数和方向。滑动达到上限仍未找到时结束该目标，不进入无边界滚动。

### 4.6 锚点恢复

每个目标执行完成后按照以下顺序恢复：

1. 系统返回，并使用页面指纹验证是否回到锚点。
2. 按页面栈继续返回，直到达到最大恢复次数。
3. 重启 APP 并重放起始导航。
4. 仍无法恢复时中止本次执行，标记 `anchor_recovery_failed`。

### 4.7 安全护栏

- 删除、支付、注销、解散、提交订单等动作默认禁止。
- 高风险目标必须人工确认后才能进入任务。
- 坐标点击只能作为已知截图和设备尺寸归一化后的兜底。
- AI 不得绕过风险校验直接下发 ADB 操作。
- 任务需要保留执行动作审计和风险跳过原因。

## 5. 前端交互方案

AI 探索页面保留一个统一入口，创建任务时首先选择模式：

- `目标巡检（推荐）`
- `自由探索（高级）`

目标巡检配置重点收敛为：

1. 选择项目、应用和设备。
2. 配置起始导航并实时验证目标页面。
3. 批量输入目标清单，或从当前截图框选加入目标。
4. 配置有限滑动和风险边界。
5. 保存并执行。

报告默认展示目标覆盖矩阵：

- 已找到并生效。
- 已找到但状态未确认。
- 未找到。
- 风险跳过。
- 偏航后恢复。
- 执行异常。

点击目标结果后再展开前后截图、框选范围、页面证据、日志和技术定位信息，避免报告首页过度臃肿。

## 6. AI 放权路线

### L0：报告分析

AI 只读取执行结果并解释问题。当前平台已基本具备。

### L1：巡检计划生成

AI 根据页面地图生成目标清单、优先级和下一轮巡检草稿，保存前由人工确认。

### L2：受控动作建议

执行过程中 AI 可以在平台提供的安全候选动作中选择，但不能构造任意坐标或 ADB 命令。

### L3：有限自主探索

AI 可以在已批准页面范围、最大深度、动作预算和风险护栏内自主规划，平台负责执行和回滚。

### L4：跨任务学习

AI 根据历史复核结果、页面地图变化和缺陷反馈调整策略。正常业务行为必须通过规则化复核沉淀，避免同类误报重复出现。

## 7. 开发节奏

### 第一阶段：基础重构（2026-07-15 ～ 2026-07-17）

- 增加执行批次模型并兼容历史任务。
- 新增 `target_inspection` 策略。
- 建立执行器分发和设备适配接口。
- 创建目标巡检执行器骨架和基础单元测试。

验收：旧自由探索能够继续执行；新模式能够创建任务并生成独立执行记录。

### 第二阶段：目标巡检闭环（2026-07-20 ～ 2026-07-24）

- 实现目标逐项定位、有限滑动和证据采集。
- 实现点击、Switch、弹窗和列表状态变化判断。
- 实现锚点返回、重启 APP 和起始导航重放。
- 增加目标结果 API 和实时进度。

验收：以社区首页为基准，只操作目标清单中的控件，找不到时不点击无关控件。

### 第三阶段：页面地图和报告（2026-07-27 ～ 2026-07-29）

- 持久化页面节点、控件和跳转关系。
- 建设目标覆盖矩阵和页面证据交互。
- 支持执行批次对比和页面地图增量更新。
- 生成语义元素候选，但不自动发布到正式语义库。

验收：能够查看页面、控件、跳转关系以及每个目标的完整证据链。

### 第四阶段：AI 规划接入（2026-07-30 ～ 2026-07-31）

- AI 分析输入改为结构化页面地图和目标结果。
- 生成下一轮巡检目标和优先级。
- 生成语义命名建议和自动化用例草稿。
- 所有 AI 建议保存前需要人工确认。

验收：AI 能够基于真实覆盖缺口生成可执行巡检草稿，不直接操作手机。

### 第五阶段：稳定性打磨（2026-08-03 起，预计 2～4 周）

- 多分辨率、多 Android 版本和多品牌设备回归。
- 动态页面指纹优化和误报规则沉淀。
- 页面地图版本差异和 UI 改版影响分析。
- 性能指标、logcat 和缺陷证据统一关联。
- 评估 L2 受控动作建议，不直接进入完全自主控制。

## 8. 阶段验收指标

- 已配置目标识别率不低于 85%。
- 锚点恢复成功率不低于 95%。
- 非目标控件误点击率低于 5%，首版社区首页场景目标为 0。
- 高风险动作自动执行次数为 0。
- 目标证据完整率为 100%。
- 同一任务连续执行三次，结果一致率不低于 90%。
- 页面地图重复节点率低于 10%。
- 报告能够明确区分 APP 缺陷、定位失败、环境问题和正常业务行为。

## 9. 首批开发任务顺序

切换开发模型后严格按照以下顺序执行：

1. 新增 `AppExplorationRun` 和 `AppInspectionTargetResult`，完成迁移与兼容测试。
2. 调整任务运行 API，使每次执行创建独立批次，不再删除历史步骤。
3. 新增执行器分发器和 `TargetInspectionRunner` 骨架。
4. 前端增加“目标巡检”模式及目标清单字段。
5. 实现单目标精确查找、点击、状态判断和证据落库。
6. 扩展为多目标队列、有限滑动和锚点恢复。
7. 完成社区首页真机验收后，再开始页面地图持久化。

## 10. 暂不纳入首版

- 大模型实时裸控手机。
- 无边界随机遍历。
- 自动执行支付、删除、注销等高风险业务。
- AI 建议未经确认直接写入正式语义库。
- 依赖 OCR 作为主要定位方式。
- 首期同步开发 iOS 执行器，但接口设计必须兼容后续 iOS 接入。
